# v0.2.1 laptop remote-access repair

Based on main 50232979e0b48c64db0c321ce2c24e122a7bcedd (v0.2.0).

## Findings

- The laptop Agent and desktop were v0.2.0; Agent, sshd and WireGuard were running. The desktop processes belonged to the logged-in local user.
- sshd listened only on the laptop tunnel IP. Agent remote sessions and diagnostics hard-coded 127.0.0.1:22, which refused connections. Configure `sshAddress` from the actual local listener instead of changing sshd_config.
- Desktop button messages omitted coordinates and depended on a previously throttled pointer move. A click could use a stale cursor position. A received frame alone does not verify input delivery.
- The laptop had no shared proxy configuration. Its existing Clash HTTP and SOCKS5 listeners both completed HTTPS requests, returning 200. The Net Conductor loopback policy proxy is a different service and must not be shared back to itself.

## Changes

- Discover loopback/tunnel SSH listener and custom port during installation. Preserve sshd_config and existing authorized keys. Reuse installed sshd when Windows capability metadata is inconsistent instead of unconditionally reinstalling the component.
- Validate configured SSH targets against loopback or this device's tunnel IP, retaining pinned SSH host-key verification.
- Expose signaling and authenticated desktop-poll readiness separately from Agent connectivity; report missing proxy sharing and stopped local proxy targets.
- Add automatic, P2P-only and relay-only selection. Relay-only works without SDP/ICE. Existing automatic mode still waits approximately 12 seconds after offering before falling back.
- Start desktop in view-only mode. Explicitly enable control; include coordinates with button events and combine movement/click in a Windows INPUT event. Keep keyboard verification separate from frame verification.
- Remove guessed proxy port defaults and explain the local listener, private shared listener and server exit-policy steps.

## Verification completed

- `go test ./...`, including address restrictions, authenticated desktop job handoff, existing P2P RPC, relay without SDP, and recovery when a test proxy target starts.
- `go vet ./...`; Windows amd64 and Linux amd64 builds.
- Two Playwright regression tests: relay-only file session, and view-only desktop plus coordinate-bearing mouse events and separate keyboard events. These tests mock the backend; they do not assert native input acceptance.
- Existing production HTTPS certificate successfully validated against the saved enrollment certificate. Frontend remote assets and authenticated server SSH-public-key endpoint returned 200.
- Actual laptop HTTP 33210 and SOCKS5 33211 proxy HTTPS requests returned 200.
- Added a laptop private HTTP share on the same numeric port, forwarding tunnel-IP:33210 to loopback:33210. Both firewall and application allow only the server tunnel IP as source. No prior shares were replaced.

## Pending acceptance (do not mark as passed)

- Installing the repair requires the user's Windows UAC confirmation. At this checkpoint the running version remains v0.2.0.
- Server administrative SSH access lacks a verified host-key entry; the requested connection details/fingerprint are pending. No password guessing or host-key bypass was performed.
- Production webpage SSH, SFTP round trip and file mutation tests, both production P2P and HTTPS/WebSocket relay paths, desktop frames and isolated native keyboard/mouse tests, server-side proxy settings/exit policy and actual server-through-laptop Internet access remain unverified.
- The powered-off desktop was neither contacted nor awaited; original-machine desktop-browser reproduction is unavailable.
- No OS reboot, intentional network outage, WireGuard stop, automatic third-party proxy startup, server initialization or removal of shared components was performed.

## Safe native-input acceptance procedure

Use a headless controller or a controller on the public server so the laptop browser cannot steal focus. Open a dedicated unprivileged test window in the laptop's logged-in desktop. Verify its title, foreground identity and screenshot immediately before each input sequence; abort if focus changes. Click only inside its known bounds, type a unique harmless marker, verify the window's contents, then verify key release. Repeat over P2P and relay independently. Do not classify screenshots or simulated DOM events as successful native input.
